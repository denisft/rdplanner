# Реестр требований resource-planner

Единственный источник истины по вопросу «что уже реализовано, а что только описано».
Заменяет замороженный снимок «Реализовано на дату» — статус живёт здесь и обновляется при каждом деплое.

- **PRD** (`resource-planner-PRD.md`) отвечает на «зачем и как» (проблема, user story, acceptance).
- **Этот файл** отвечает на «в каком оно состоянии» и даёт доказательство — ссылку на код/тест, а не галочку по памяти.
- **releasenote.md** — журнал «что и когда уехало на прод»; колонка «Релиз» связывает реестр с ним.

## Словарь статусов

| Значок | Статус | Что значит |
|--------|--------|------------|
| ✅ | реализовано | Есть код и (для движка) зелёный тест; видно на проде |
| 🟡 | частично | Часть требования закрыта, часть — нет (в примечании: что осталось) |
| 🔧 | в работе | Начато, на прод ещё не уехало |
| 📝 | описано | Есть спека (раздел PRD / acceptance), кода нет |
| 🔍 | discovery | Ещё нет концепции, требуется проработка |
| ⬜ | не начато | В беклоге, к работе не приступали |

**Правило проверки:** статус ✅ ставится только если можно показать файл и — для логики движка — зелёный тест. «Кажется, сделали» = не ✅.

**Как поддерживать:** при деплое на прод (скилл `deploy-prod`) — если релиз закрывает или двигает требование, переставить его статус здесь и вписать дату релиза. Это шаг ритуала деплоя, а не отдельная дисциплина.

## Продуктизация: от пет-проекта к продукту (2026-07-25)

Итог продуктового анализа «что нужно, чтобы rdplanner стал полноценным продуктом».
Главный тезис: «полноценный продукт» ≠ отказ от анти-требований PRD §3. Zero-friction
(без аккаунтов, без сервера, план по одной ссылке) — это и есть позиционирование;
продуктизация — это доверие, порог входа, надёжность данных и гигиена, а не гонка
фич с Float/Runn. Ядро дифференциации остаётся прежним: БЛ-1 (объяснимость) и БЛ-2
(what-if) — они выше любого пункта ниже, кроме дыр безопасности.

## Спеки продуктизации (ПРОД / СЕК / UX)

Лёгкие спеки под требования из раздела выше. Формат: проблема → что делаем → готово когда. Колонка «Спека» в таблицах ведёт сюда по якорю-идентификатору. Полноценные acceptance для больших фич (БЛ-1, БЛ-2) остаются в PRD §7–8; здесь — то, чего в PRD нет.

### ПРОД-1
**Модель распространения и лицензия.** Проблема: репозиторий публичный, но без файла LICENSE он юридически «все права защищены» — никто не вправе форкнуть или самостоятельно захостить, а это противоречит обещанию «бесплатно, без регистрации». Что делаем: Денис выбирает модель (open-source с разрешительной лицензией типа MIT + бесплатный хостинг на Vercel / только хостинг без исходников), добавляем `LICENSE` в корень и строку о лицензии в README. Готово когда: файл LICENSE есть в репо, README называет модель, на лендинге сказано «бесплатно и почему».

### ПРОД-2
**Позиционирование: README + лендинг.** Дубль БЛ-8 — держим здесь ради полноты трека. Проблема: у продукта нет внятного «для кого и чем лучше Float/таблиц». Что делаем: README и `SITE/` по формуле из PRD §9, текст «от Дениса» через voice profile. Готово когда: README и лендинг несут позиционную формулу; объяснимость (БЛ-1) уже в обещании. Спека — PRD §9.

### ПРОД-3
**Privacy-friendly аналитика.** Проблема: о пользователях не известно ничего — сколько заходят, доходят ли до первого плана, пользуются ли шарингом/отчётом; развитие идёт вслепую. Что делаем: счётчик без cookies и ПД (Plausible-класс или свой endpoint), события: визит, создан первый план (первая задача), нажат «Поделиться», открыт отчёт, открытие плана по ссылке. Никаких имён/содержимого плана. Готово когда: события летят, есть дашборд с воронкой «зашёл → первый план», сбор описан в политике приватности (СЕК-5).

### ПРОД-4
**Канал обратной связи в приложении.** Проблема: аудитория анонимна, спросить пользователя не у кого. Что делаем: ненавязчивая кнопка «Написать» → форма или `mailto:` на почту Дениса. Готово когда: из приложения можно отправить отзыв в один клик, письма доходят.

### ПРОД-5
**Праздники: производственный календарь.** Проблема: движок считает нерабочими только сб/вс — вокруг длинных праздников (майские, новогодние) даты релизов заведомо врут, а это ядро ценности продукта. Что делаем: настраиваемый список нерабочих дат сверх пн–пт, исключается из слотов наравне с выходными; хранение в `AppData` (уходит в файл и в ссылку — общий факт плана, не личная настройка вида). Готово когда: заданная дата-праздник не занимается ни одним этапом, дата релиза сдвигается, поведение покрыто тестами в `src/engine/*.test.ts`.

### ПРОД-6
**Английская локаль интерфейса.** Проблема: интерфейс только на русском — потолок аудитории. Что делаем: вынести строки UI в словарь, переключатель RU/EN, даты в нейтральном формате. Решение и приоритет — за Денисом (может остаться 🔍). Готово когда: весь UI переключается на EN без обрезанных строк.

### СЕК-1
**CSV-инъекция в выгрузках.** Проблема: `cell()` в `src/export/csvExport.ts` экранирует только кавычки и `;`. Имя задачи вида `=HYPERLINK(...)` или `+cmd` из плана, открытого по чужой ссылке, выполнится формулой при открытии CSV в Excel/LibreOffice — реальный вектор, т.к. содержимое плана приходит извне. Что делаем: во всех CSV-выгрузках (`csvExport`, `weeklyLoadCsv`, `taskSizingCsv`) значение, начинающееся с `=` `+` `-` `@` (а также tab/CR), префиксуем апострофом или заворачиваем — по OWASP «CSV Injection». Готово когда: ячейка с ведущим `=/+/-/@` не исполняется как формула, добавлен тест на инъекцию рядом с существующими CSV-тестами.

### СЕК-2
**Security-заголовки.** Проблема: `vercel.json` не отдаёт ни одного security-заголовка. Что делаем: через `headers` в `vercel.json` — `Content-Security-Policy` (self + Upstash endpoint для fetch), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (или `frame-ancestors` в CSP). Готово когда: ответ прод-домена содержит заголовки, приложение и шаринг работают (CSP не рубит легитимный fetch к `/api/*`).

### СЕК-3
**Минимальная длина id плана на записи.** Проблема: `PLAN_ID_RE` пускает id от 6 символов — короткие id перебираемы, а план по ссылке-id доступен на чтение без секрета. Фактически клиент шлёт UUID, но сервер это не требует. Что делаем: в `/api/save` для новых планов требовать id ≥16 символов из `[a-zA-Z0-9_-]`; на чтении (`/api/load`) правило не менять, чтобы старые короткие ссылки продолжали открываться. Готово когда: попытка записать план с коротким id отклоняется 400, старые планы читаются, поведение покрыто в `planGuards.test.ts`.

### СЕК-4
**CI на каждый push.** Проблема: `.github/workflows/` нет — тесты, сборка, lint и `npm audit` держатся только на ручной дисциплине скилла `deploy-prod`. Что делаем: workflow (GitHub Actions) на push/PR: `npm ci` → `npm test` → `npm run build` → `npm run lint` → `npm audit --audit-level=high`. Деплой на прод — только с зелёным CI. Готово когда: workflow гоняется на каждый push, красный CI виден до деплоя.

### СЕК-5
**Публичная политика приватности.** Проблема: предупреждение перед первой публикацией есть, но публично нигде не сказано, что именно уходит на сервер, насколько и как отозвать. Что делаем: короткая страница (лендинг или раздел README): при шаринге на сервер уходят имена сотрудников, отпуска и структура плана; хранение — Upstash Redis, TTL год с продлением на чтении/записи; чтение по id, перезапись/отзыв только по editKey; «Отозвать ссылку» удаляет план. Плюс перечень событий аналитики (ПРОД-3). Готово когда: политика доступна по ссылке, на неё ведёт сноска из окна публикации.

### UX-1
**Первый запуск.** Проблема: новичка встречает пустой гант, а «Демо-данные» спрятаны в меню «Файл» — до ага-момента (движок сам посчитал даты релизов) можно не дойти и уйти. Что делаем: пустое состояние с короткой подсказкой пути «добавьте людей → заведите задачу → даты посчитаются сами» и заметной кнопкой «Показать на демо-данных». Готово когда: на чистом localStorage виден онбординг-экран, демо стартует в один клик.

### UX-2
**Дискаверимость жестов ганта.** Проблема: ключевая механика (drag = закрепить `pinnedStartDate`, dblclick = открепить, Alt+dblclick = редактировать) живёт только в тултипах — её не найти, пока случайно не потянешь. Что делаем: иконка «?»/легенда жестов рядом с гантом, раскрывает список жестов. Готово когда: все жесты ганта описаны в видимой из UI справке, не только в hover-тултипе.

### UX-3
**Read-only ссылка на телефоне.** Проблема: ссылку из чата часто открывают с телефона, а гант рассчитан на десктоп — горизонтальная каша. Не мобильное приложение (анти-требование PRD §3 в силе), только сносный адаптив режима просмотра. Что делаем: для `?plan=...` на узком экране — читаемая раскладка (горизонтальный скролл ганта в контейнере, не ломающий страницу; таблица релизов первым экраном). Готово когда: план по ссылке на ширине телефона читается без «разъехавшейся» вёрстки.

### UX-4
**Защита от потери данных.** Проблема: localStorage — единственная копия плана; очистка данных браузера уносит его молча и целиком. Для продукта — недопустимый режим отказа. Что делаем (минимум): ненавязчивое напоминание «сохраните в файл» после N изменений с момента последнего сохранения; опционально — локальный автобэкап (последние снимки в отдельном ключе) с восстановлением. Многопользовательская синхронизация не вводится (анти-требование). Готово когда: пользователя предупреждают до потери, есть путь восстановления хотя бы из файла.

### UX-5
**Клавиатурная доступность и контрасты.** Проблема: закрепить этап можно только мышью (drag&drop), фокус-навигации по ганту нет — недоступно с клавиатуры и для скринридеров. Что делаем: способ закрепить/открепить этап без мыши (например, выбор этапа + перенос стрелками/полем даты), проверка контрастов палитры MatDash по WCAG AA. Приоритет за Денисом (может остаться 🔍). Готово когда: сценарий «завести задачу и закрепить этап» проходится с клавиатуры, контрасты проходят AA.
